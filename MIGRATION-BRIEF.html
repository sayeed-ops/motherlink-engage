01Current system summary

ML Studio is an internal Next.js 16.2.5 application — motherlink-app/ inside the ML Studio folder — serving Motherlink employees. It is a small, young codebase: 63 files under src/, 88 tracked files, 9 commits, no tests of any kind. Confirmed

It has two halves that barely know each other. A platform shell provides Firebase email/password auth, a three-role model, a feature registry that renders the dashboard and sidebar, invitations by email, activity logs, and system settings. A feature registry entry called reddit-visibility points at the Reddit Visibility Assistant, which is where essentially all the real product value lives. The other three registered features (image-generator, writing-assistant, seo-assistant) are placeholders — two are coming_soon and the third is explicitly isPlaceholder: true. Confirmed

So the honest framing of this project: you are not extracting a module from a platform. You are extracting the only working product from a shell that was built to host products that were never built. That materially changes the recommendation in section 20 — there is much less "shared" code to preserve than the framing of the task assumes. Inferred

Everything runs against a single Firebase project, motherlink-studio. Documentation states dev and prod share it, with no staging project. Confirmed

02Current Reddit tool architecture

The tool spans three deployables, only one of which is in the Next.js build. Confirmed

The web app — 21 files

Ten pages and layouts under src/app/(apps)/apps/reddit-visibility/, four API routes under src/app/api/reddit-visibility/, four components, and seven library files under src/lib/reddit-visibility/. The centre of gravity is [projectId]/opportunities/page.tsx at 1,591 lines — it holds the fetch loop, analysis loop, filtering, draft generation, the account picker, and job dispatch.

The pure-compute API pattern — the single most important architectural fact

All four API routes are stateless. None of them touches Firestore. They receive {project, sources, post} from the browser, call DeepSeek or Reddit, and return a result that the client then persists using the Firebase browser SDK. Confirmed

Consequence you cannot design around

Because writes happen in the browser under the user's own credentials, firestore.rules is the only server-side authority in the entire system. There is no middleware.ts, no firebase-admin in the Next app, no verifyIdToken anywhere in src/, and no session cookie. Any authorization model for Engage that assumes a trusted server tier is a rewrite of this layer, not a port of it. Confirmed

The four routes

All four are POST-only, declare no runtime or maxDuration, and perform zero authentication. Anyone who can reach the deployment can burn your DeepSeek credits and your metered IPRoyal residential bandwidth. Confirmed

The local posting agent — reddit-poster-agent/index.mjs

A 443-line Node process that runs on one Mac beside AdsPower. It authenticates with firebase-admin and a service-account.json file, which means it bypasses firestore.rules entirely. It polls reddit_post_jobs every 5 seconds, claims the oldest queued job inside a real Firestore transaction that re-reads and re-checks status (so double-claiming is genuinely safe), then drives a real AdsPower browser profile over CDP to post on old.reddit. Confirmed

Its safety controls are the most carefully built part of the whole system: logged-in username verification by DOM read with abort on mismatch, thread-identity verification, account rails re-checked against live state, rolling 24-hour counters, post-submit verification that refuses to claim success unless the comment is really live, human-like typing with jittered think-pauses, and DRY_RUN. Confirmed

The Electron wrapper — motherlink-poster/

A macOS menu-bar app that fork()s the unmodified agent with injected env, so a non-technical operator needs no terminal, Node, or pm2. Auto-starts at login. Untracked in git. Confirmed

Security rules — three gaps

Rules findings
  • Three collections have no rules at all. reddit_accounts, reddit_post_jobs, and reddit_agent_status appear nowhere in firestore.rules, and there is no catch-all match. Under the rules as committed, the Accounts page and the entire auto-post queue would be denied by default. Since the feature demonstrably works, the deployed rules almost certainly differ from the file in the repo. Confirmed (file) Unknown (deployed)
  • Every Reddit rule is allow read, write: if isSignedIn(). Any authenticated user can read and write every client's projects, posts, drafts, and accounts. There is no per-project isolation whatsoever. The file says so: // TODO: tighten to a feature-access check once rules are migrated. Confirmed
  • Invitations are enumerable. allow read: if isSignedIn() && (isAdmin() || request.query.limit == 1) — the limit == 1 escape hatch exists so signup can look up a token, but it lets any signed-in user read invitation docs, including tokens, one at a time. Confirmed

Six composite indexes are declared in firestore.indexes.json — and here is a subtlety worth carrying forward: the code deliberately does not use most of them. Every list query is a flat where('projectId','==',…) with no orderBy, sorted client-side, with an explicit comment that this avoids needing a composite index. The index file is largely aspirational. Confirmed

05Authentication and authorization assessment

This is the weakest area of the current system, and the one place where I recommend against preserving current behaviour.

How it works today

Firebase email/password. Signup is invitation-token-only and entirely client-side: read ?token=, query invitations, validate expiry in the browser, create the user, then write users/{uid} with the roleId and roleSlug taken from the invitation document. Three roles — super_admin, admin, employee — with six boolean management permissions on the role doc, plus hasAllFeatureAccess and per-user assignedFeatureIds. Confirmed

Findings

  • RouteGuard does not guard. It renders {children} unconditionally once loading is false; the redirect is a useEffect side effect. Protected content renders for at least one frame for unauthenticated users. Confirmed
  • Suspended users hit a redirect loop. The guard pushes to /login?error=account_suspended without calling signOut(), so firebaseUser remains set, which re-triggers the "logged in, don't show login" branch back to /. Confirmed
  • Invitation tokens use Math.random() — not cryptographically secure, and generated in the browser. Confirmed
  • /api/send-invitation is an unauthenticated open email relay. No auth check, no rate limit, no origin check, and role / invitedByName are interpolated raw into the HTML. Anyone can make Resend send Motherlink-branded mail. Confirmed
  • Any admin can mint a super_admin invitation — the rules only check isAdmin(), and the UI dropdown offers Super Admin, despite admin having canManageRoles: false. Confirmed
  • /seed is a public unauthenticated route. Rules narrow the window on a non-empty database, but the page itself is ungated. Confirmed
  • NEXT_PUBLIC_SUPER_ADMIN_EMAIL is configured but never read by any code. Super-admin is purely the Firestore roleSlug field. Confirmed
Implication for Engage

Your requirement that "all sensitive authorization must be enforced server-side and through Firestore security rules" cannot be met by porting this code. There is no server-side authorization to port. This part must be redesigned — see sections 10 and 12. Inferred

Tribal knowledge that must survive extraction

This is the highest-value, least-recoverable asset in the project, and it lives in prose docs rather than code. If Engage is rebuilt without it, someone will re-walk every dead end — and two of them risk your accounts:

  • Why RSS, not the JSON API. Tried in order: Apify (worked, slow, $45/mo actor, code fully removed) → direct .json returns HTTP 403 for this network → old.reddit scraping returns 429 → Python scrapers (wrong stack, all punt to proxies) → official OAuth API. RSS is the only endpoint returning 200, and only with a real browser User-Agent through a rotating residential proxy.
  • The API is closed to you. Reddit's Nov-2025 Responsible Builder Policy gates approval 2–4 weeks. Per the progress report: "our promotional use case won't pass — applying honestly can even flag the accounts. Confirmed by trying to register an app."
  • Reading and posting need opposite proxy types. Rotating for reads; sticky-forever-per-account for posts. Inverting this gets accounts banned.
  • The dirty-IP saga. The shared rotating pool scored 82/100 on IPQS fraud — couldn't log into Gmail, Outlook, or Reddit through it. Fix was IPRoyal ISP static with the "0-fraud-risk IP" option → fraud ~0. This is a purchase decision encoded as a war story.
  • No VPS needed. The proxy determines the IP Reddit sees regardless of where code runs. Oracle free tier was explored, hit capacity limits, abandoned.
  • undici is server-only (needs node:net) — this is the only reason redditFetch.ts and throttle.ts are separate files. Merge them and you break the client bundle.
  • Three agent bugs already paid for: in-page fetch('/api/me.json') hangs, so username is read from the DOM; the submit button must be found inside the same <form> as the textarea (old.reddit has hidden per-comment forms) with a native el.click() fallback — "the hardest bug: the button was always found; the click just didn't land"; and never assume success — "it used to false-report POSTED."
  • Prompt-version semantics. Analysis v3 introduced growthScore — posts analyzed before v3 have no growthScore and will not appear in the Growth bucket until re-analyzed. Draft v2 fixed a capitalization regression. Migrate analyses without understanding this and the Growth bucket silently under-fills.
  • RSS parsing quirks. Bodies are double-encoded HTML (decode up to 4×); strip the submitted by /u/… footer; RSS carries no score or comment count, hence the zero-metric defaults and the UI hiding them.

Confirmed — all of the above is documented in reddit-tool-complete-guide.md, REDDIT_PROGRESS_REPORT.md, and REDDIT_VISIBILITY_HANDOFF.md.

The double-posting question, answered precisely

If Engage and ML Studio both write to reddit_post_jobs, and one agent drains it, nothing double-posts — the transactional claim guarantees a job is claimed once. If you run two agents against the same queue, the transaction still prevents the same job posting twice, but the two agents evaluate rate rails concurrently and could exceed a daily cap. Confirmed

This gives you a clean strategy for the whole migration, which section 14 builds on: the queue is the safe integration point. Point both apps at one queue, keep exactly one agent, and the posting layer never needs to be migrated twice.

Agent defects to fix in Engage (not to preserve)

  • No lease or TTL on claimed jobs. An agent crash strands a job in posting forever. attempts is incremented but never checked, so there is no max-attempt cap, and the UI has no cancel path. Confirmed
  • The username check is skippable. If expectedUsername is empty, the check degrades to a log warning and posts anyway from whatever account is open — contradicting the README's claim that it can never post from the wrong account. Confirmed
  • deleteProjectCascade leaves reddit_post_jobs behind. A queued job for a deleted project would still be claimed and posted to Reddit. Confirmed
  • Rate-limit logic is implemented three times — accountPostGate in the UI, gate() in the agent, recordAccountPost/nextCounters on the write side — and is already visibly drifting (different reason strings, different null-handling). Confirmed
  • DRY_RUN marks jobs failed, which is terminal — a dry-run job can't be promoted to a real post without re-queuing. Electron defaults dryRun: false while the agent's .env ships DRY_RUN=1. Confirmed

10Recommended target architecture

All of this section is Recommended unless marked otherwise.

Keep what the current design gets right

Three decisions in the existing system are load-bearing and should survive unchanged: Firestore as the message bus between the web app and the local agent (no VPS, no queue service, no open ports); credentials never stored in the product (they live in AdsPower profile state); and every analysis and draft stamped with model + promptVersion + token counts for cost attribution and reproducibility. Confirmed as current behaviour

Change the authorization tier — this is the one structural change I recommend

The current pure-compute + client-writes design cannot express "user X may fetch posts on project A but not approve on project B." Rules alone can enforce membership, but the six-way permission model you described needs a trusted tier. Concretely:

  • Add firebase-admin and a server tier. Route handlers verify an ID token, load the caller's project membership, and enforce the permission before doing work. This closes the four unauthenticated routes as a side effect.
  • Move Reddit writes server-side. Persisting through the server is what lets rules become restrictive rather than permissive.
  • Use custom claims for coarse-grained facts (isAdmin, tenant id) so rules can check them cheaply without a get(), and Firestore membership docs for fine-grained per-project permissions. Claims are capped at 1000 bytes — do not put a permission matrix in them.
  • Rules become defence-in-depth, not the only defence. Default deny; explicit allow per collection; no isSignedIn()-only rule on any collection holding client data.

Make the platform dimension real from day one

Reddit is currently implicit — it is the reddit_ prefix on eight collections and the word "Reddit" in the UI. For Quora and LinkedIn to be additive rather than a second rewrite, the platform must become data, not a naming convention: a platform discriminator field, a per-platform module registry, and platform-specific config nested under a project rather than parallel to it. Section 11 shows the shape.

Keep the agent exactly as it is for v1

The agent is the most battle-tested component and the least coupled — it talks only to Firestore and AdsPower, and knows nothing about ML Studio. Change its Firebase project config and nothing else. Fix the defects in section 7 after parity is signed off, not during.

12Recommended auth, invitation, and permission model

All Recommended.

Two layers, deliberately separated

Global role — who you are on the platform: owner, admin, member. Governs user management, project creation, billing. Stored on users/{uid} and mirrored into a custom claim for cheap rule checks.

Project permissions — what you may do on one client. Stored on projects/{id}/members/{uid} as an explicit array. Not mirrored into claims: a user on 30 projects would blow the 1000-byte claim limit.

Proposed permission set

You asked me to recommend rather than assume. Your list is close, but I would make three changes based on what the code actually does:

PermissionGatesNote vs. your list
project.viewRead project + items + draftsAs proposed
project.editEdit config, subreddits, forbidden phrasesAs proposed
project.membersAdd/remove members, set their permissionsAs proposed

Dropped from your list: "review opportunities" as a single permission — reading is project.view, and the expensive parts are items.analyze / drafts.generate. The distinction that matters is not view vs. edit, it is free vs. spends money vs. touches the public internet.

Bundles, not roles

Ship named presets (Viewer / Analyst / Approver / Manager) that expand to permission arrays at assign time. Store the expanded array, not the bundle name — so changing a preset later never silently re-grants permissions on existing projects.

Invitations — fix all four defects

  • Generate tokens server-side with crypto.randomUUID(), never Math.random() in the browser.
  • Store a hash of the token, so the limit == 1 read escape hatch cannot leak a usable token.
  • /api/send-invitation must verify the caller's ID token and their permission before sending, and escape all interpolated fields.
  • An invite carries projectId + permissions, so accepting it lands the user in the right client with the right access.
  • Verify the Resend sending domain — today it uses the sandbox onboarding@resend.dev.

Route protection

Replace the current client-only RouteGuard. Guard rendering by returning null while unauthenticated rather than redirecting as a side effect, and enforce every real decision in the route handler. Client-side checks become a UX nicety, not a security control.

15Data migration approach

The hard problem: identity

Every Reddit document carries createdBy — a Firebase Auth UID from motherlink-studio. A new Firebase project mints new UIDs for the same humans. Nothing errors; attribution just silently becomes wrong. Confirmed

Two options, and I recommend the first: Recommended

  • Recreate users and remap. Create each user in Engage, build an oldUid → newUid map keyed by email, and rewrite createdBy during transform. Users set a new password once. Clean, auditable, no legacy baggage. Viable because the user count is small.
  • Import the Auth users via firebase auth:export / auth:import, preserving UIDs and password hashes. No remap needed, no password reset — but it needs the source project's hash config and carries every legacy account forward.

Unknown: how many users exist and whether preserving passwords matters. Question 4 in section 19.

Order — dependency-first

  1. Backup. A full managed export of motherlink-studio to GCS. Verify it restores into a scratch project before touching anything.
  2. Users → build the UID map.
  3. Projects — one projects/{id} envelope per current reddit_projects doc, with fields moved to modules/reddit. Record oldProjectId → newProjectId.
  4. Members — no source data exists; today anyone signed-in sees everything. This must be authored by you, not migrated. It is the moment access control comes into existence.
  5. Sources → re-parent.
  6. Posts → items. The bulk. Preserve the deterministic id, processingStatus, and isFavorite exactly — isFavorite is a purge-retention flag, so losing it silently loses data on the next fetch.
  7. Analyses — preserve promptVersion verbatim. Do not backfill growthScore; a missing value is meaningful.
  8. Drafts — preserve status and posted attribution. Posted drafts are the answered-ledger that stops the tool re-engaging a thread.
  9. Accounts — copy postCountToday, postCountResetAt, lastPostAt at freeze time. Stale counters mean the first day in Engage could exceed a daily cap. Verify each adsPowerProfileId still resolves.
  10. Jobs — do not migrate. Drain to zero instead (section 17).
  11. Agent status — do not migrate. The agent rewrites it within 5 seconds.
  12. Activity logs — copy last-N for continuity, or archive. Low value, high volume.

Method

A standalone Node script using firebase-admin with two service accounts (source read-only, destination write). Idempotent — deterministic destination ids so a re-run overwrites rather than duplicates. Emits a reconciliation report: per-collection counts, unmapped-UID count, field-checksum comparison. Never run it against production before it has run clean against staging twice. Recommended

Timing — the constraint that shapes everything

The tool is in daily use, so a copy taken early is stale by cutover. Do the real production copy inside the cutover window, with writes frozen — not weeks ahead. The dry run in phase 04 is what makes that window short and boring.

16Testing and parity checklist

Starting position

There are zero tests today. There is no baseline to compare against and no regression suite to inherit. Parity must be established by observation on real data. Confirmed

Parity — same inputs, same outputs

  • Fetch: same subreddit, same limit, both apps within a short window → same redditPostId set (allowing for genuinely new posts). Same deterministic doc ids.
  • Analysis: same post + project + sources → same decision, and score within a tolerance. DeepSeek is non-deterministic even at temperature: 0.2 — parity means "same bucket and same relevant sources", not identical scores. Inferred
  • Prompts: byte-identical buildAnalysisPrompt / buildDraftPrompt output. This is exactly testable — diff the strings. Assert ANALYSIS_PROMPT_VERSION === 'v3' and DRAFT_PROMPT_VERSION === 'v2'.
  • Draft eligibility: the brand/growth gate and GROWTH_MIN = 40 reproduce identically. Note it is currently duplicated between the route and the UI — unify it, then test the one copy.
  • Filtering: QUALITY_FLOOR (best: 75, good: 60, okay: 40) buckets the same post set.
  • Rate gate: accountPostGate returns identical decisions across the cap/interval/banned/flagged matrix. Unit-test this properly — it is pure, it is the safety rail, and it is currently implemented three times.
  • Purge: the retention invariants hold — favorites survive, posts-with-drafts survive, onlySubreddits scoping means a failed subreddit never wipes another's posts, an empty run never wipes anything. Test this hard; it is the most destructive path in the system.
  • Proxy: both IPRoyal formats parse; Basic-token auth is used, not URL-embedded; 429 retry honours Retry-After.
  • RSS parsing: feed fixtures → identical NormalizedRedditPost. Include a double-encoded body to pin the 4× decode loop.

Data parity after migration

  • Per-collection counts match the reconciliation report. Zero unmapped createdBy.
  • The promptVersion distribution is unchanged — same count of pre-v3 analyses, so the Growth bucket under-fills identically. A "fixed" Growth bucket means the migration corrupted something.
  • isFavorite and posted-draft counts match exactly.
  • Account counters match at freeze time.

New tests that must exist before cutover

  • Rules tests against the emulator: a member of project A cannot read project B; an unauthenticated caller reads nothing; a viewer cannot publish. This is the whole point of the migration — it must be proven, not assumed.
  • Route auth tests: every handler rejects an absent or invalid token. Explicitly cover the four routes that are open today.
  • Job lease test: a claimed job with an expired lease is reclaimable — the defect from section 7.

The one test that cannot be automated

A real post to a real subreddit from Engage. The agent's failure modes — the form-scoped submit button, the click that doesn't land, the false POSTED — are only observable against live Reddit. Do one DRY_RUN=1 pass, then one real low-stakes post, watched by a human. Recommended

17Cutover strategy

Everything before this is reversible. This is not. Recommended

The governing insight

There is exactly one agent, and it can only drain one queue. That makes cutover a single, atomic, well-defined act: repoint the agent's Firebase config. It is not a DNS switch or a traffic split — it is one config change on one Mac. Everything else is preparation.

Sequence

  1. Announce a freeze. Small team, so this is a message, not a system.
  2. Stop queueing in ML Studio. Disable the publish button. Do not stop the agent — it must finish what is in flight.
  3. Drain to zero. Watch reddit_post_jobs until no job is queued or posting. Resolve anything stuck in posting by hand — there is no lease, so a stranded job never resolves itself, and you must know whether the comment actually went live before deciding.
  4. Stop the agent. Both pm2 and the Electron app — remember it auto-starts at login and can be running unnoticed. Confirm via the heartbeat's pid going stale.
  5. Freeze writes. Flip ML Studio's rules to read-only for reddit_*. This is the real freeze — a rules change, not a social agreement.
  6. Final backup. Managed export. This is your rollback point.
  7. Run the migration. Already rehearsed twice in staging. Check the reconciliation report.
  8. Repoint the agent at the Engage Firebase project. Start with DRY_RUN=1.
  9. Verify dry-run: queue a job from Engage → agent claims it, opens the right profile, verifies the right username, types, stops. This proves the whole chain minus the irreversible click.
  10. DRY_RUN=0, one real post, low-stakes subreddit, human watching. Confirm the permalink is live and the draft/post/counter writes all landed.
  11. Enable publishing in Engage. Unfreeze. Cutover complete.
  12. Leave ML Studio's Reddit feature deployed and read-only for the soak.
Cannot be migrated without manual intervention — flagging explicitly, as you asked
  • AdsPower profiles. Reddit sessions are browser state on one Mac, bound to specific sticky IPs. No export path. The agent must keep running on that machine. If it ever moves, every account re-authenticates through its own sticky IP — the single riskiest operation in the system, and worth doing never rather than casually.
  • Project membership. No source data exists. You author it by hand.
  • Passwords, unless you use the Auth export/import path.
  • In-flight jobs. Drained by hand, not migrated.
  • Secret Manager entries, if App Hosting turns out to be the live target — recreated by hand in the new project, never copied through a file.
